# Interactive Rest Timer Live Activity Design

## Goal

Add `-15s` and `+15s` controls to the active rest timer in the iOS Lock Screen Live Activity and expanded Dynamic Island. The controls must update the visible countdown and the rest-completion notification immediately while the React Native app is backgrounded, then reconcile the in-app timer when the user returns.

This is a rest-only vertical slice. Weight, reps, RPE, set completion, skip-rest, and non-rest controls are explicitly out of scope.

## User Experience

### Lock Screen

While a rest is active, retain the existing exercise name, set counter, countdown, and proportional progress bar. Add a bottom control row with two 44-point buttons:

- `-15s` on the left
- `+15s` on the right

The Live Activity may grow up to the system's 160-point Lock Screen height allowance. A tap updates the countdown in place without opening the app. If `-15s` moves the deadline to the present or earlier, the rest ends immediately and both controls disappear.

### Dynamic Island

- Compact and minimal presentations remain read-only.
- The expanded presentation adds the same `-15s` and `+15s` row below the progress bar.
- iOS 16 keeps the current read-only presentation. Controls are available on iOS 17 and later.

### Feedback and accessibility

- Use `Button(intent:)`, not tap gestures, so the controls have native interaction and VoiceOver behavior.
- Give the buttons explicit accessibility labels: "Decrease rest by 15 seconds" and "Increase rest by 15 seconds."
- Mark the countdown and progress bar as invalidatable content so the system can show that an intent-driven refresh is pending.
- Do not add a skip button or other actions during this experiment.

## State Model

Use a single versioned `RestTimerSnapshot` stored in the existing App Group. This is ephemeral cross-process timer state, not workout history and not a second database.

The snapshot contains:

- schema version
- rest session ID
- Live Activity ID
- exercise name
- current set number and total sets
- absolute rest deadline in epoch milliseconds
- maximum rest duration used as the progress denominator
- whether the rest is active
- last-updated timestamp
- writer (`javascript` or `intent`)

JavaScript creates a new session ID when a rest starts, writes the snapshot after every in-app start or adjustment, and removes it when the rest or workout stops. The native intent mutates the same snapshot while the app is backgrounded.

The absolute deadline is authoritative. Neither side reconstructs it from a rounded remaining-seconds value.

## Native Architecture

### Shared Swift sources

Add shared Swift sources for the snapshot store and two `LiveActivityIntent` implementations. The Expo config plugin copies and registers the sources in the targets required by the widget UI and App Intents runtime. The ActivityKit attribute schema used by the intent must remain byte-for-byte compatible with the schema generated by `expo-live-activity`.

The config plugin remains idempotent: repeated clean prebuilds must not duplicate file references or build-phase entries.

### Intent execution

`DecreaseRestIntent` and `IncreaseRestIntent` perform the following sequence through a process-local Swift actor so rapid taps are serialized:

1. Read the current App Group snapshot.
2. Reject the action if the snapshot is missing, inactive, or already expired.
3. Apply `-15,000` or `+15,000` milliseconds to the absolute deadline.
4. Grow the progress denominator only for `+15s`; never shrink it for `-15s`.
5. Write the updated snapshot before refreshing presentation state.
6. Update the matching Live Activity by its stored activity ID. Preserve the existing exercise title and `Set X/Y|D` subtitle transport format, pass the new absolute deadline, and move `staleDate` to the new deadline.
7. Replace the stable `liftai-rest-complete` local notification so it fires at the new deadline.

If `-15s` reaches zero, the intent writes an inactive snapshot, updates the Live Activity to the existing non-rest set presentation, and removes both pending and delivered rest notifications.

The intent never selects the first available ActivityKit activity; it targets the persisted activity ID so another app activity cannot be mutated accidentally.

### Notification behavior

Native notification scheduling mirrors the existing JavaScript behavior:

- identifier: `liftai-rest-complete`
- title: `Rest Complete`
- body: `Time for your next set`
- default sound
- time-sensitive interruption level

Every reschedule removes the pending request and any delivered notification with the stable identifier before adding the replacement. Native operations are awaited rather than launched fire-and-forget.

## React Native Reconciliation

The existing rest hook owns foreground behavior. On an `active` AppState transition it reads the shared snapshot before computing remaining time:

- If the snapshot matches the current rest session and remains active, copy its deadline and progress denominator into the hook refs and React state.
- If it matches but is inactive or expired, end the rest without a second vibration because the native notification already owns background alerting.
- If it belongs to another session, ignore it.

Reconciliation does not reapply a delta, reschedule the notification, or push a second ActivityKit update. The native intent already completed those effects. This prevents the double-adjustment and notification races present in the removed polling design.

No action queue or 500ms poller is introduced. App Group reads happen only at rest lifecycle boundaries and foreground reconciliation.

## Error Handling

- Missing or malformed snapshots make the intent a safe no-op.
- An ActivityKit update failure does not discard the updated snapshot; React Native can still reconcile the timer on foreground.
- A notification failure does not roll back the deadline. The Live Activity remains the primary visible timer.
- Swift logs intent failures with `Logger`. JavaScript bridge and reconciliation failures are reported to Sentry.
- Stopping a rest removes the shared snapshot so stale controls cannot mutate a later rest.

## Testing

### Automated

- Snapshot encoding and decoding round-trip with all required fields.
- Starting a rest creates a fresh session and snapshot.
- In-app `+15s` grows both the deadline and denominator.
- In-app `-15s` changes only the deadline.
- Foreground reconciliation adopts a matching intent-written deadline exactly once.
- Foreground reconciliation ends an inactive or expired matching rest without duplicate vibration.
- A stale session snapshot is ignored.
- Stop and workout cleanup remove the snapshot.
- Static native-source tests verify both intents, stable notification identifier, activity-ID targeting, and iOS 17 availability gates.
- Existing rest timer, Live Activity, notification, and TypeScript suites remain green.

### Native verification

Because this feature adds Swift files, run `npx expo prebuild --clean`, then build and install on a physical iPhone from the main checkout.

Verify:

1. `+15s` changes the locked-screen countdown and delays the notification.
2. Two rapid `+15s` taps add 30 seconds rather than losing one update.
3. `-15s` changes the countdown and advances the notification.
4. `-15s` at 15 seconds or less ends the rest and cancels the notification.
5. Returning to the app shows the same deadline and progress as the Live Activity.
6. The expanded Dynamic Island controls work; compact and minimal remain read-only.
7. An untouched locked rest exits countdown presentation at its deadline, rechecking the existing `staleDate` risk.

## Success Criteria

- Both controls work without opening the app on iOS 17 and later.
- Rapid taps are cumulative and do not corrupt the deadline.
- Lock Screen, expanded Dynamic Island, in-app timer, progress denominator, and notification converge on one absolute deadline.
- No action queue, polling loop, duplicate notification, or unrelated workout mutation is introduced.
- The read-only iOS 16 and compact/minimal presentations are unchanged.
